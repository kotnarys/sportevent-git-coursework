# Иерархическая структура работ (ИСР) проекта SportEvent

Модель жизненного цикла — **каскадная с проверкой результатов на каждом этапе**. Структура основана на результатах этапов; Git-ветки показывают соответствие жизненному циклу. См. также `WBS.csv`.

```text
1.0 SportEvent
├─ 1.1 Инициация и анализ [stage/analysis]
│  ├─ 1.1.1 Определение заинтересованных сторон
│  ├─ 1.1.2 Анализ предметной области
│  └─ 1.1.3 Согласование требований и границ MVP
├─ 1.2 Проектирование [stage/design]
│  ├─ 1.2.1 Модель данных
│  ├─ 1.2.2 Прототип пользовательского интерфейса
│  └─ 1.2.3 Проектирование бизнес-правил и ролей
├─ 1.3 Реализация [stage/implementation]
│  ├─ 1.3.1 Каталог соревнований и участников
│  ├─ 1.3.2 Регистрация на мероприятия
│  ├─ 1.3.3 Расчёт результатов и экспорт
│  └─ 1.3.4 Локальное сохранение
├─ 1.4 Проверка качества [stage/testing]
│  ├─ 1.4.1 Автоматические тесты
│  ├─ 1.4.2 Ручные приемочные сценарии
│  └─ 1.4.3 Проверка ошибок ввода
└─ 1.5 Выпуск и сопровождение [stage/deployment]
   ├─ 1.5.1 Инструкция по запуску
   ├─ 1.5.2 Релиз v1.0.0
   └─ 1.5.3 Размещение публичной версии на GitHub (требует публикации)
```

## Правила работы с ветками

- `main`: интегрированный и протестированный код.
- `stage/analysis`: документация требований.
- `stage/design`: проектные решения.
- `stage/implementation`: функциональный прототип.
- `stage/testing`: тесты и сценарии проверки.
- `stage/deployment`: выпуск и инструкции.

В учебной локальной истории каждая ветка имеет собственную контрольную точку (коммит). Полноценная командная работа предполагает pull request перед переносом изменений в `main`; права доступа к GitHub задаются в настройках удалённого репозитория.
